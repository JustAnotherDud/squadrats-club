# squadrats-club

Club site for the squares (squadrats and squadratinhos) a running club has
captured on [Squadrats](https://squadrats.com): club map, profiles, places,
history and gains, served by GitHub Pages from `main`.

`fetch-map-data.yml` runs 6 times a day. It reads each athlete's squares from
Squadrats' vector tiles, builds the JSON files and publishes them to the `data`
branch only when something changed. The pages read those files from
`raw.githubusercontent.com/JustAnotherDud/squadrats-club/data/data/...`, so
publishing data never rebuilds Pages.

## Data contract

`folha-do-clube` reads three files from this repo. Their names, paths and
format must not change:

| File | Branch |
|---|---|
| `data/squadrats.json` (totals per athlete) | `data` |
| `data/daily_gains.json` (gains per day) | `data` |
| `data/membros_cores.json` (athlete colours) | `main` |

The full list of generated files is `env.FILES` (plus `data/atletas/` and
`data/regioes/`) in `fetch-map-data.yml`. They are git-ignored on `main`. To
work with them locally:

```
git checkout origin/data -- data/
```

Static files (border geojsons, `adjacency.json`, `membros_cores.json`) live in
`data/` on `main`.

## Site

- `index.html`: hub with links to the other pages.
- `club.html`: map of every athlete's squadratinhos, drawn on canvas. Own
  squares in the athlete's colour, shared ones in a neutral scale by number of
  owners. Panel with overlap, per-athlete and per-region leaderboards.
- `atletas/`: one profile per athlete (`<slug>.html`) and an index. Stubs are
  generated by `pipeline/gen_profile_stubs.py`; `perfil.js` and `perfil.css`
  do the work from `data/atletas/<slug>.json`.
- `lugares/`: one page per place with activity: PT concelho (`c-`) and
  distrito (`d-`), foreign region (`<cc>-r-`) and zone (`<cc>-z-`), and
  country (`pais-<cc>`). Stubs are generated by `pipeline/gen_lugar_stubs.py`;
  `regiao.js` and `comum.js` render them from `data/regioes/<key>.json`.
  `lugares/index.html` (hand-written) lists every place from
  `data/regioes_index.json`. `regioes/index.html` only redirects there.
- `historico.html`: event feed (overtakes, new leaders, first presence,
  milestones) from `data/events.json`.
- `ganhos.html`: every squadratinho gain window from `data/ganhos.json`.
- `analise.html`: the map owner's detailed personal map (first athlete in
  `ATHLETES_JSON`). Left out of the navigation on purpose.
- Shared code: `shared.js` (vocabulary, XYZ grid, data URLs, formatting,
  warnings), `nav.js` (top bar, injected by each page except `analise.html`;
  also registers `sw.js`), `site.css` (tokens and primitives), `fonts/`
  (self-hosted, see `fonts/README.txt`).
- PWA: `manifest.json`, `sw.js` (caches the static shell only) and the icons
  generated by `pipeline/gen_icons.py` (needs `pymupdf` and `pillow`).

On `localhost` the pages read `data/` from the working copy instead of raw.

## Pipeline

`pipeline/run_all.py` runs every step in one process, so each athlete is
scanned once:

1. `build_analise.py`: owner's squares classified by region, trophies and
   suggestions (`tile_info_*.json`, `stats.json`, `trophies.json`,
   `suggestions.json`).
2. `fetch_club_totais.py`: totals per athlete (`squadrats.json`) and
   `daily_gains.json` (see `daily_gains.py`).
3. `fetch_club_squares.py`: every athlete's squadratinhos with a bitmask of
   owners (`club.json`). The order of `ATHLETES_JSON` fixes the bits: do not
   reorder without regenerating the file.
4. `classify_club.py`: counts per region, per athlete and for the club union
   (`club_regioes.json`).
5. `append_events.py`: new events from the day-by-day history of
   `club_regioes.json` on `origin/data` (`events.json`, logic in `eventos.py`).
6. `append_ganhos.py`: gain windows between consecutive runs (`ganhos.json`).
7. `append_regioes.py`: one file per place plus the index (`regioes/`,
   `regioes_index.json`, logic in `regioes.py`).
8. `append_gains_regioes.py`: daily gains per region (`gains_regioes.json`).
9. `build_profiles.py`: one bundle per athlete (`atletas/`).

Only steps 1 to 3 touch the network, through `tiles_fetch.py`. Classification
is in `classify.py` (largest intersection area, proximity fallback on the
coast); grid maths in `kml_parse.py`.

`ATHLETES_JSON` holds `{"name": "firebase_uid", ...}`. In CI it is a repo
secret; locally, export it by hand. To run everything (the `append_*` steps
read the history of `origin/data`):

```
py -m pip install -r requirements.txt
git fetch origin data
git checkout origin/data -- data/
py pipeline/run_all.py data
```

### Manual tools

Not run by the workflow:

- `compute_grid_totals.py`: total squares per region, written to
  `refdata/grid_totals.json`. Re-run when borders or the classification rule
  change.
- `compute_adjacency.py`: region neighbours and map colours
  (`data/adjacency.json`). Re-run when borders or the clip set change.
- `refdata/prep.py`: rounds and simplifies the border files (`--check` only
  compares).
- `refdata/clip.py`: see "Foreign municipalities" below.
- `backfill_*.py`, `recon_snapshots.py`: rebuild `daily_gains.json`,
  `events.json` and `gains_regioes.json` from the history of the `data`
  branch.

## What each layer's `size` means

| Layer | `size` is |
|---|---|
| `squadrats` / `squadratinhos` | number of squares visited |
| `yard` / `yardinho` | squares in the largest closed cluster |
| `ubersquadrat` / `ubersquadratinho` | the N of the largest full NxN square |

A closed square is visited and has its 4 neighbours (N/E/S/W) visited.
`suggestions.py` refuses to publish if it cannot reproduce the server's yard
and übersquadrat.

## Vector-tile endpoint usage rules

`tiles1.squadrats.com/{uid}/trophies/{ts}/{z}/{x}/{y}.pbf` is not a public or
documented API. The athletes' maps are public and the UID is in the map URL.
To avoid abuse:

- At most 6 runs a day. Recompute the worst-case request count before raising
  it.
- Identifiable `User-Agent` and low concurrency (`DISCOVERY_CONCURRENCY=4`,
  `FETCH_CONCURRENCY=6` in `tiles_fetch.py`).
- Publish only derived aggregates, never raw tiles.
- Keep `{ts}` fresh on every request (`int(time.time()*1000)`): the server
  ignores it, but it is part of the URL.
- A 1-request probe per athlete compares the global squadratinhos total with
  the last published one. Only athletes who changed get the full scan.
- The full scan uses the z10 tiles cached in `data/scan_cache.json`. If the
  reconstruction does not match the server's `size`, it runs the z4 → z7 → z10
  discovery and refreshes the cache.
- Every published count must match the server's `size` exactly, otherwise
  the run fails instead of publishing.

## Places and borders

- PT: GADM 4.1 concelhos and distritos. Calheta and Lagoa carry their region
  in the name (`Calheta (Açores)`, `Lagoa (Faro)`) so they do not collide.
- Abroad: `refdata/foreign/<CC>.geojson` (regions) and
  `refdata/foreign_muni/<CC>.geojson` (municipalities). Regions exist for ES,
  DE, MA and AD, municipalities for ES, DE and MA (AD uses its parishes for
  both).
- Other countries: `refdata/outlines/europe.geojson` (Natural Earth, public
  domain) gives the country only. The site shows a flag and "sem dados por
  região", and a warning bar asks for manual work.
- `refdata/` holds the precise borders used to classify; `data/` holds
  simplified copies used only to draw.

### Foreign municipalities

`refdata/foreign_muni/<CC>.full.geojson.gz` is the full GADM 4.1 set
(`{country, region, parent}`, 6 dp, gzipped). Only `clip.py` reads it.
`refdata/foreign_muni/<CC>.geojson` is what `classify.py` loads: only the
municipalities within 10 km of a captured square. It is generated by
`clip.py`; never edit it by hand.

When a member rides somewhere new:

1. New country: download the country from GADM 4.1 (level 4 GeoJSON),
   reshape each feature to `{country, region, parent}`, disambiguate duplicate
   names, round to 6 dp, minify and gzip to
   `pipeline/refdata/foreign_muni/<CC>.full.geojson.gz`. For a region level,
   also add `refdata/foreign/<CC>.geojson` and both to `prep.py`'s table.
2. Run the clip: `git checkout origin/data -- data/club.json`, then
   `py pipeline/refdata/clip.py <CC>` (no argument: all countries). It
   rewrites `<CC>.geojson` and prunes `grid_totals.json`. Commit both.
3. If the kept set changed, run `py pipeline/compute_adjacency.py` and commit
   `adjacency.json`.

Squares outside the clip classify to region only. The run log prints
`AVISO: ... fora do recorte de 10 km` and the site shows a warning bar.

## Tests

`tests/harness.py` checks that the pipeline and the site behave as recorded in
`tests/baseline.json`. It runs the unit tests, three pipeline runs against a
fake Squadrats tile server (three fictional athletes), and every page type in
Microsoft Edge through Playwright. No requests go to Squadrats; only Leaflet
comes from its CDN. Large outputs are stored as count + hash.

Setup, once:

```
py -m venv .venv
.venv/Scripts/python -m pip install -r tests/requirements.txt
```

Run:

```
.venv/Scripts/python tests/harness.py
```

`--update` rewrites the baseline after an intended change. Without Edge, run
`playwright install chromium` and set `HARNESS_BROWSER=` (empty).
`python -m pytest` alone runs only the unit tests (as CI does).

## Workflows

- `fetch-map-data.yml`: the pipeline, 6 times a day, plus
  `workflow_dispatch`. It also regenerates the profile and place stubs on
  `main` when the set changes, and commits `heartbeat.txt` when `main` has had
  no commit for 25 days, so GitHub does not disable the schedule.
- `tests.yml`: `pytest` on pushes and pull requests that touch `pipeline/`.

## Debugging: "the map stopped updating"

1. The run fails with a count mismatch: the scan was incomplete. The log names
   the layer and UID.
2. `SquadratsHttpError` (500): the UID is invalid. Check that
   `squadrats.com/map/{uid}/17` still opens.
3. The endpoint changed or is blocked: there is no fallback;
   `tiles_fetch.py` has to be rewritten for the new source.
4. GitHub disabled the schedule: run `fetch-map-data.yml` once by hand.
